# 002 按库存动态生成 AI 菜谱

配置模型后，每日生成和换菜从模型获取本次候选菜谱。日常使用无需维护固定菜谱。当用户确认做菜时，按已保存菜单的食材清单写入库存；历史保存当时的参考用量和做法。

| 验收场景 | 预期 |
|---|---|
| 库存有足够食材，模型返回合格候选 | 系统从候选选出三道不同的三人份家常菜，至少一道含肉和一道纯素 |
| 模型返回缺货食材、未知代码、格式异常、汤或主食 | 排除不合格候选。候选不足时按菜单状态提示；模型错误或输出无法使用时显示可重试错误 |
| 换一道 | 给模型原菜单菜名以生成新候选，系统保留两道原菜及原槽位 |
| 同一个写入请求重试 | 返回已保存的结果，库存保持不变 |
| 模型响应期间，库存或菜单版本变化 | 重新校验，冲突时要求重试 |
| 模型不可用 | 原菜单与库存保留，页面提示重试 |

应用使用已登记食材代码验证用料。第一版动态候选允许充足及常备食材；由于库存“少量”没有三人份用量保证，暂时不用于模型生成候选。换菜时保留原菜仍按其原规则校验。库存自然语言录入共享模型配置。菜单生成和换菜由模型提出候选，后端校验用料和组合约束。

## 配置方式

编辑项目根目录的 ai-config.yaml，在 ai 节点下填写 url、model 和 api_key，保存后重启后台。ai-config.example.yaml 提供空白示例。实际配置已加入 .gitignore。也可使用以下环境变量，逐项覆盖文件配置：

| 变量 | 值 |
|---|---|
| MENU_AI_URL | 模型服务的完整 chat-completions URL |
| MENU_AI_MODEL | 服务端支持的模型名 |
| MENU_AI_KEY | 服务要求 Bearer 认证时填写 |

随后按现有运行说明重启 FastAPI。外部服务会收到符合条件的食材名称、分类、库存档位以及换菜需要排除的菜名。库存预览会把用户输入原文和已登记食材名称及别名发送给配置的模型服务。应用正常运行时，未配置模型则库存预览、需要重新生成的菜单和换菜返回可重试错误。启用后下一次需要生成菜单或换菜时走模型，已确认的菜单保持冻结。

实现包括 chat-completions 适配器、响应校验、与 SQLite 菜单事务和 H5 的集成。模拟模型和响应解码已通过自动化测试；真实服务联调待选定模型后执行。


## 代码与配置分离规则

本项目后续新增或修改功能时，模型地址、模型名称、密钥和其他部署相关参数统一通过独立配置文件或环境变量提供。业务代码只负责读取、校验和使用配置。AI 配置文件使用 YAML，路径基于项目目录定位，切换终端工作目录后仍能读取。

配置优先级为环境变量覆盖文件中的对应字段。配置中字符串必须使用字符串类型，空值使用双引号包围的空字符串。空文件或缺少文件视为未启用 AI；格式错误、字段类型错误或地址与模型配置不完整时，启动报错，错误信息不得包含密钥。真实配置加入 Git 忽略列表，示例配置仅含空白值。配置修改后重启后台生效。

验收时用临时配置验证文件读取、环境覆盖、空配置和格式错误，同时运行现有菜单回归测试。

生成与换菜失败时，后台记录操作和失败原因。手动请求的 503 响应和页面提示区分未配置、连接失败、超时、上游 HTTP 错误、额度不足、响应格式异常及菜谱候选未通过校验。定时任务共用诊断日志。日志仅包含操作、固定原因代码和上游状态码。

菜谱生成和换菜调用模型时取消应用层连接和读取超时，旧菜谱超时配置不再生效。库存识别仍使用 35 秒。网络或上游主动中断时沿用原有错误诊断。

## 后台换菜任务

单换和整换接受后立即返回 HTTP 202 与任务 ID，页面查询任务状态（排队、运行、成功、失败）。等待时保留当前菜单并显示进度，成功后更新菜单，失败时显示原有错误详情。同一请求键重复提交复用任务，参数不同则报冲突。单进程本地实例同一时间只接受一项换菜任务，并保留最近 128 项任务状态。任务状态随后台进程重启清空，已保存的菜单和成功请求的幂等记录继续保存在 SQLite。菜单及库存版本仍在提交数据库前校验。
